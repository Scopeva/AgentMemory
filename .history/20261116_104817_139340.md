### Assistant
“Agent 记忆工具”通常指让 AI Agent 跨会话保存和检索信息的机制。按实现位置可分为四类：

### 1. 会话内上下文管理
- **Context Window**：短期工作记忆，存放当前对话历史、工具结果等。
- **Compaction/Summarization**：上下文过长时自动压缩、摘要旧对话，保留关键信息。
- 常见于 OpenAI 的 prompt caching、Claude 的 context editing 等系统层面。

### 2. 长期记忆（持久化）
- **向量数据库（RAG 式记忆）**：把事实/偏好 embedding 后存入 pgvector、Milvus、Pinecone 等，检索时按相似度召回。
- **知识库 + 检索**：把记忆以 Markdown 文件、数据库表等形式存盘，agent 用 grep/SQL 检索，如 Claude Code 的 `MEMORY.md`、Cursor 的 project rules。
- 典型开源项目：**MemGPT**（把记忆分层为 core/external memory，类 OS 分页）、**Zep**（时序 + 图记忆）、**Letta**（MemGPT 商业化）。

### 3. 结构化记忆层
- **事实型**：用户档案（姓名、偏好、项目状态），以键值或图谱形式存。
- **经验型**：把过去成功/失败的工具调用、episode 摘要存入，供未来 agent 参考，代表系统有 **Mem0**（轻量记忆层，开源 + 云服务）、**LangMem**。
- **图谱型**：用知识图谱保存实体和关系，适合复杂多跳推理。

### 4. 框架内置 API
- **LangGraph / LlamaIndex / CrewAI / AutoGen / OpenAI Agents SDK**：都有 memory 抽象，底层通常接向量库或 KV 存储。
- **Claude Code 风格**：用文件（`CLAUDE.md`、memory 文件）+ 工具读写实现“外置记忆”，简单但可调试。

选型建议：
- 只要用户偏好 → 简单 KV/JSON 文件就够。
- 大量非结构化经验 → Mem0 或自建 RAG。
- 复杂多 agent 共享状态 → 向量库 + 知识图谱 + 版本控制。

```

├── AGENTS.md          # 共享状态 / 待办 / 决策记录（所有 agent 都读）
```

### 方案 B：加一个轻量记忆服务（多项目 / 复杂经验时更优）

如果不想全靠文件，可以在本机跑一个小型服务，统一暴露“记忆读写 API”：

- 存储：本地 SQLite + 向量索引（如 sqlite-vec / Chroma 本地实例）
- 接口：`save(agent, task_id, content)`、`recall(agent, task_id, query)`、`list_open_tasks()`
- 三个 agent 通过 shell 脚本或 MCP 服务器调用同一 API

这样：
- 跨 agent 共享的是**结构化经验**（试过什么、失败原因、结论），而不是原始聊天记录。
- 切换 agent 时：新 agent 先 `recall(task_id)`，再根据返回摘要继续。

### 方案 C：统一用 MCP server 暴露记忆（最标准）

做一个本地 MCP server（Python/Node 均可），提供：

- `memory.read(key)` / `memory.write(key, value)`
- `session.handoff(task_id)` / `session.resume(task_id)`

然后给 Codex、OpenCode、Pi（如果 pi 支持 MCP 或可调用 CLI 工具）都挂上这个 MCP。三者对同一套记忆，切换成本降到最低。

### **Zep**
- **特点**：时序感知记忆，内部维护知识图谱，适合需要“关系推理”的场景（比如“用户上次说喜欢 X，这次问 Y”）。

### **Letta（原 MemGPT）**
- **特点**：把记忆分层为 core memory + archival memory，agent 可以主动分页加载/卸载，适合长任务、多轮深度工作。
- **MCP 支持**：社区有适配层。
- **适合**：如果你希望 agent 能自己管理“现在记住什么、忘掉什么”。

| 部署成本 | 单个 Python 文件，本地跑，无外部服务 |
| 数据可见性 | SQLite 是纯文本库，`sqlite3` CLI 随时查，调试方便 |

## 具体设计（贴合编程开发）

```
handoff server 提供 4 个工具：

1. task.list()
   → 返回当前所有 open task 及其最后更新 agent

2. task.read(task_id)
   → 返回结构化 handoff：
   {
     "task_id": "auth-migration",
     "last_agent": "codex",
     "updated_at": "2026-11-16T16:50:00Z",
     "status": "in_progress",
     "summary": "JWT refresh token 已实现，单元测试 3/5 通过",
     "next_steps": ["修复 refresh token 过期边界 case", "补 integration test"],
     "verified_facts": ["token 存 localStorage", "refresh 端点 /api/auth/refresh"],
     "open_questions": ["是否要加 CSRF 保护？"],
     "files_touched": ["src/auth/token.ts", "tests/auth.spec.ts"]
   }

3. task.write(task_id, agent, payload)
   → 覆盖更新该 task 的 handoff 记录

4. task.close(task_id, agent, summary)
   → 标记完成，归档
```

关键点：
- **`files_touched`** 字段非常重要——切换 agent 时，新 agent 直接读这几个文件就能快速进入上下文，比读全量 chat history 高效得多。
- **`verified_facts`** 避免新 agent 重复验证（比如 Codex 已经确认了某个 API 行为，OpenCode 不用重新查）。
- **一个 task 一条记录**，而不是按 agent 隔离——这正是你要的“共享”。

- 专为 coding agent 设计的持久化记忆，支持 **handoff baton（交接棒）**：一个 agent 完成任务后打 baton，owner 标记接受，下一个 agent 接手。
- 有明确的 task 状态管理（accepted / done / failed）。
- 2026 年 11 月 9 日还有活跃使用记录，相对 obsmcp 更新。

## 2. swarm-mcp（跨 agent 协作）

**仓库**：`Volpestyle/swarm-mcp`

- 设计目标就是"多个 MCP server session 在同一台机器上互相发现、协作"。
- 共享一个 SQLite 文件（`~/.swarm-mcp/swarm.db`），所有 agent 都指向它。
- 提供 `dispatch`（派任务）、`spawn`、handoff 完成状态跟踪（done / failed / cancelled）。
- 每个 agent 通过 stdio 拉起自己的 swarm agent 进程，对 agent 本身零侵入。
- **适合你的场景**：Codex、OpenCode、Pi 三个 agent 共享同一个 `swarm.db`，任务在它们之间流转。

## 3. monomindcli（重型方案，含代码知识图谱）

**仓库**：`monoes/monomindcli`

- 针对 Claude MCP、OpenCode、Codex 等多 agent 协调。
- 内置 **tree-sitter 代码知识图谱** + persistent memory + session hooks + SQLite 任务协调。
- 如果你以后想要"agent 自动理解代码结构 + handoff"，这是最完整的方案。
- 比 swarm-mcp 重，适合项目规模变大后再上。

## 4. 自建 FastMCP + SQLite（仍然推荐作为兜底）

如果上面现成方案都不完全满足，自建 150 行左右其实是最快的——因为你只需要 4 个工具（task.list / task.read / task.write / task.close），SQLite 单表就能撑住。好处是：

- 数据格式完全可控，调试方便
- 没有外部依赖，不会"7 个月没更新"
- Pi 的 wrapper 也最简单

- **事件幂等**：`event_id` 为主键去重，`(run_id, sequence_no)` 唯一约束防止同 run 内序列重复。
- **乐观锁**：knowledge 和 task 更新都带 `revision` 条件，影响 0 行时返回冲突，不静默覆盖。
- **候选记忆与正式知识分离**：`memory_candidates` 是 Agent 提交的待审记录，`knowledge` 是已接受的长期记忆，生命周期独立。
- **uuid 在 Python 生成**：不用 `uuidgen()` SQLite 函数（不是内置的），由应用层 `uuid.uuid4()` 生成后写入。

关键设计：
- **Spool 路径**：`~/.local/state/agent-memory/pi/`，每个 agent 独立子目录
- **At-least-once delivery**：spool 中事件只有在服务端返回 200/204 后才标记 `acknowledged` 并删除
- **服务端不可达时**：自动降级写 spool，不丢失事件
- **`flush_spool()`**：重试所有 pending 事件，全部 ack 后清空

### 2. Pi Adapter — `adapters/pi/pi_adapter.py`

三个内部模块：

| 模块 | 职责 |
|---|---|
| `SessionObserver` | 记录 Pi 生命周期事件（session_start, run_started, turn_end, compaction, settled, interrupted） |
| `MemoryCaptureController` | 判断是否请求记忆提取（防递归 + 跳过 trivial runs） |
| `RunGuard` | 进程内 `run_id` 级别的递归防护，同一 run 最多一次提取 |

**防递归规则**：
- `origin == "memory_extraction"` → 拒绝再次提取
- `extraction_attempted == True` → 拒绝
- 只有 `completed/failed/interrupted` 且有 code changes 或 task significance 才触发
